## 3. 가장 중요한 두 가지

### 3-1. 청구범위를 "유사도 측정"에 두면 안 됩니다

얼굴 임베딩의 코사인 유사도로 신원 일치도를 측정하는 것, 프레임별 유사도의 분산으로
시간 안정성을 나타내는 것은 **이미 학술계 표준 평가 지표**입니다. 이것을 독립항의
요지로 삼으면 신규성·진보성에서 어려움을 겪을 가능성이 높습니다.

방어 가능한 지점은 **폐루프**입니다.

```
기준 미달 객체·구간 특정 → 오류 유형에 대응하는 조건 변경
   → 해당 부분만 재생성 → 재검증 → 이력 축적
```

종래 문헌은 측정에서 끝나고 교정 루프가 없습니다. 상세는 `03_선행기술_및_청구전략.md`.

### 3-2. 출원 전까지 공개하지 마십시오

현재 GitHub 저장소와 기술명세서 모두 비공개이므로 신규성 상실 사유가 없습니다.

다만 **벤처기업 기술평가, 투자 IR, 데모 시연에서 기술 내용을 설명하면 공지가 될 수
있습니다.** 출원 전에 이런 일정이 있다면 다음 중 하나를 택하십시오.

- 출원을 먼저 하고 설명한다 (권장)
- 비밀유지계약(NDA)을 체결하고 설명한다
- 부득이 공개했다면 **공지예외주장을 12개월 내에** 반드시 신청한다

## 4. 변리사에게 확인받아야 할 사항

`03_선행기술_및_청구전략.md` §7에 정리했습니다. 요약하면,

1. **미구현 요소를 청구할지** — 객체 단위 조건 변경(청구항 20안)이 아직 구현되지
   않았습니다. 오류 객체를 특정하는 데까지는 되지만 그 정보가 생성 요청에 반영되지
   않습니다. 출원 전 구현할지, 종속항으로만 둘지, 제외할지 판단이 필요합니다.
2. **임계값 수치를 명세서에 넣을지** — 영업비밀 유지와 실시가능요건 사이의 균형입니다.
   현재 초안은 산출 *방법*을 기재하고 구체적 수치는 실시예에만 넣었습니다.
3. **해외 출원 여부** — 미국을 고려하면 §101(추상적 아이디어) 대응을 위해 "생성 조건을
   변경하여 재생성한다"는 **기술적 제어** 성격을 지금부터 명세서에 강조해 두는 편이
   유리합니다.
4. **발명자 표시** — 아래 §5 참조.

## 5. 발명자 표시에 관하여

**착상과 설계는 사람이 하였고, 구현 코드 작성에는 생성형 AI(Claude)를 활용했습니다.**
저장소 커밋에도 그 사실이 기록되어 있습니다.

특허법상 발명자는 자연인이어야 하며 AI는 발명자가 될 수 없습니다. 다만 이 사안에서
**발명의 착상 자체는 사람이 한 것**으로 보입니다. 근거는 다음과 같습니다.

| 근거 | 자료 |
| --- | --- |
| 발명의 구조를 기술명세서로 사람이 먼저 정의 | Confluence 기술명세서 v1.1 (개발 착수 기준) |
| 해결 과제와 접근 방식을 사람이 제시 | PoC 개발 요구사항 문서 |
| "인코더가 발명의 핵심이 되면 안 된다"는 청구 전략을 사람이 결정 | 개발 지시 이력 |
| 아키텍처 판단과 그 근거를 사람이 검토·승인 | `docs/adr/` |

즉 AI는 **착상의 구체화 수단**으로 사용되었습니다. 다만 이 판단은 변리사가 최종
확인해야 하며, 출원서에 사실과 다른 기재를 해서는 안 됩니다.

> 참고: 저작권 등록은 이와 별개의 문제입니다. 저작권 쪽은 AI 산출물의 등록 가능성이
> 더 까다롭게 다뤄집니다. `~/Desktop/CREZ_저작권등록/등록절차_가이드.md` §1 참조.

## 6. 출원 절차 개요

| 단계 | 내용 | 담당 |
| --- | --- | --- |
| 1 | 변리사 선임 및 발명 설명 (이 폴더 전달) | 발명자 |
| 2 | 선행기술조사 (특허성 판단) | 변리사 |
| 3 | 명세서·청구범위 확정, 도면 작도 | 변리사 |
| 4 | 특허출원서 제출 (특허로 `patent.go.kr`) | 변리사 |
| 5 | 출원번호 수령 → **이후 공개 가능** | — |
| 6 | 우선심사 신청 여부 결정 | 변리사와 협의 |
| 7 | (선택) 12개월 내 PCT 국제출원 | 변리사 |

**우선심사**를 신청하면 심사 기간을 크게 단축할 수 있습니다. 벤처기업 확인, 직무발명
보상 규정 보유, 특허 관련 정부지원사업 참여 등이 신청 요건에 해당할 수 있으니
변리사와 확인하십시오.

## 7. 함께 전달하면 좋은 자료

변리사가 발명을 이해하고 실시예를 보강하는 데 도움이 됩니다.

| 자료 | 위치 | 왜 유용한가 |
| --- | --- | --- |
| 기술명세서 v1.2 | Confluence `crez` 스페이스 | 발명의 전체 구조와 구현 상태 |
| `DEVELOPMENT_LOG.md` | 저장소 루트 | **자체 알고리즘의 수식과 변경 이력** — 실시예 보강에 직접 사용 |
| `docs/patent-mapping.md` | 저장소 | 청구 요소와 구현 모듈의 대응 |
| `outputs/` | 저장소 | 실측 결과 (리포트·CSV·그래프) |
| `LICENSE_NOTICE.md` | 저장소 | 제3자 구성요소 구분 — 자체 개발 범위 입증 |

특히 `DEVELOPMENT_LOG.md`에는 **개발 과정에서 발견하고 수정한 결함**이 기록되어
있습니다. 예를 들어 임계값이 동일 객체군 분포 내부에 있어 정상 프레임을 오검출하던
문제를 실측으로 발견해 조정한 이력은, 청구항 15(기준값의 결정 방법)의 실시예로
그대로 사용할 수 있습니다.

## 8. 주의사항

1. **이 문서들은 초안입니다.** 청구항 문언은 권리범위를 직접 결정하므로 반드시
   변리사가 최종 작성해야 합니다.
2. **선행기술조사를 반드시 하십시오.** 이 폴더의 조사는 방향 설정용 개괄 조사이며
   정식 조사가 아닙니다.
3. **실시예의 실측 데이터는 합성 인물 2명 기준**입니다. 표본이 작다는 점을 명세서에
   어떻게 기재할지 변리사와 상의하십시오. 실존 인물 데이터로 보강하면 더 좋습니다.
4. 명세서에 기재한 미구현 부분(객체 단위 조건 변경, 다중 인물 동시 생성 실증)은
   `03_선행기술_및_청구전략.md` §4에 정리해 두었습니다. 숨기지 말고 변리사에게
   그대로 알리십시오.
