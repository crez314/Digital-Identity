# ADR 0001 — 도메인 판정 로직을 packages/engine에 모은다

- 상태: 채택
- 일자: 2026-09-01
- 관련: 기술명세서 §2.2, §3, §10, §11

## 맥락

명세서 §3의 리포지토리 구조는 `packages/`를 contracts·db·providers·shared 네 개로 제시한다.
한편 §2.2는 다음을 요구한다.

> `crez-ml`은 DB에 직접 접근하지 않는다. 판단(합격/불합격, 재생성 여부)은 전부 `crez-api`와
> 워커에 둔다. 이렇게 해야 임계값·가중치 튜닝이 ML 서비스 재배포 없이 가능하고,
> **영업비밀 영역(Score Weight, Threshold)이 한 곳에 모인다.**

문제는 이 판정 로직의 소비자가 둘이라는 것이다.

- `apps/worker` — QC 실행, 재생성 전략 결정, 자동 매핑 확정
- `apps/api` — 수동 재생성 요청 시 전략 미리보기, 매핑 제안 조회

두 앱은 별도 프로세스이며 서로를 import하지 않는다. 판정 로직을 한쪽에 두면
다른 쪽이 HTTP로 우회 호출하거나 로직을 복제해야 한다. 복제하면
"영업비밀 영역이 한 곳에 모인다"는 요구가 곧바로 깨진다.

## 결정

`packages/engine`을 추가하고 다음을 여기에 모은다.

- `scoring.ts` — 가중합 종합 점수, §10.3 다중 인물 판정
- `rules.ts` — §10.2 오류 패턴 탐지 규칙 (DRIFT/SWAP/BLEND/TRACK_LOST/FLICKER)
- `regeneration.ts` — §11 전략 사다리, §5.1 무한 루프 방지
- `binding.ts` — §9.1 τ_assign/δ_margin 확정 판정

가중치·임계값은 이 패키지에 **하드코딩하지 않는다**. 인자로 주입받으며, 실제 값은
DB의 `qc_ruleset` 레코드에서 온다(§10). 패키지는 "규칙"을, DB는 "숫자"를 갖는다.

## 근거

- §3의 패키지 목록은 리포지토리 구조의 예시이지, 확장을 금지하는 규격이 아니다.
- 반면 §2.2의 "한 곳에 모인다"는 명시적 설계 요구다. 둘이 충돌할 때 후자를 지킨다.
- 판정 로직이 순수 함수로 분리되면 테스트가 쉬워진다. 실제로 `packages/engine`은
  DB·네트워크 없이 28건의 단위 테스트로 규칙을 고정한다 — 검증셋(Phase 2)이
  들어오기 전에도 회귀를 막을 수 있다.

## 결과

- `apps/api`와 `apps/worker`가 동일한 판정 코드를 쓴다. 복제가 없다.
- ML 서비스는 판정을 모른다. 임계값을 바꿔도 `crez-ml`을 재배포하지 않는다.
- §21 특허 매핑에서 "신원 일관성 정보 산출"과 "기준 미달 검출"의 구현 위치가
  한 파일 집합으로 특정된다.
