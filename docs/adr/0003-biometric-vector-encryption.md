# ADR 0003 — 생체 벡터를 애플리케이션 레벨에서 암호화해 저장한다

- 상태: 채택
- 일자: 2026-09-15
- 관련: 기술명세서 §4.2, §15, §16, §22 / ADR 0002

## 맥락

기술명세서 v1.3 §16이 지적한 대로 얼굴·신체 임베딩과 프로파일 centroid가 pgvector 컬럼에
평문으로 저장되어 있었다. 임베딩은 원본 사진 없이도 같은 사람을 식별·대조할 수 있는
생체 템플릿이라 개인정보보호법상 생체인식정보에 해당할 가능성이 높다(§22).
2026-09-14 실존 인물의 사진과 임베딩이 처음 들어오면서 우선 조치 대상이 되었다.

평문이 있던 곳은 다음과 같다.

| 위치 | 내용 |
| --- | --- |
| `identity_embedding.vector` | 사진별 얼굴·신체 임베딩 |
| `identity_profile.face_centroid` / `body_centroid` | 프로파일 대표 벡터 |
| `source_track.face_centroid` | 소스 영상 인물 트랙의 얼굴 대표 벡터 |
| 스토리지 `projects/*/source/*/tracks.parquet` | 프레임별 얼굴 벡터 |
| 스토리지 `identities/*` | 원본 사진 (버저닝으로 삭제·교체된 이전 버전 포함) |

## 선택지

1. **디스크·볼륨 암호화만 쓴다** — DB 계정, 덤프, 백업, 복제본으로 새면 평문이다.
   막으려는 위협(유출된 DB 사본)을 막지 못한다.
2. **pgcrypto로 DB 안에서 암호화한다** — 키를 쿼리 파라미터나 세션 설정으로 DB에 보내야 해서
   쿼리 로그·`pg_stat_statements`에 키가 남을 수 있다.
3. **비밀 회전행렬로 벡터를 난독화한다** — 코사인 유사도가 보존돼 pgvector 검색을 계속 쓸 수 있다.
   하지만 원본·변환 벡터 쌍이 차원 수만큼만 있으면 선형대수로 행렬을 복원한다. 암호화가 아니다.
4. **앱에서 AES-256-GCM으로 암호화해 bytea로 저장한다.**

## 결정

4번. 구현은 `packages/db/src/biometric.ts`.

- **키** — `BIOMETRIC_ENCRYPTION_KEY`. 실명 암호화 키(`FIELD_ENCRYPTION_KEY`)와 분리해
  생체정보만 키 파기로 폐기할 수 있게 한다. 두 키가 같거나, 운영에서 저장소 예시 키를 쓰면 기동하지 않는다.
- **형식** — `[버전 1B][IV 12B][GCM 태그 16B][float32 LE]`. pgvector와 같은 float4 정밀도라 값이 바뀌지 않는다.
- **AAD** — `테이블.컬럼:행 ID`를 인증 데이터로 묶는다. 암호문을 다른 인물의 행으로 옮겨 붙이면 복호화가 실패한다.
- **스키마** — `Unsupported("bytea")`로 선언한다. `Bytes`로 두면 `include: { profile: true }` 같은
  기본 조회 결과에 암호문이 섞여 API 응답까지 흘러갈 수 있다.

스토리지 트랙 파일에서는 벡터를 아예 뺀다(`apps/worker/src/lib/source-tracks.ts`).
QC가 이 파일에서 읽는 것은 bbox 궤적뿐이다.

원본 사진은 저장 데이터 암호화로 보호한다. 로컬 MinIO는 정적 KMS 키 + 버킷 기본 암호화(SSE-S3),
운영 S3는 버킷 기본 암호화(SSE-KMS)를 쓴다. presigned PUT·GET은 그대로 동작한다.

## 근거 — 기능 손실이 없는 이유

DB 안에서 벡터 유사도 검색(`<=>`)을 하는 코드가 없었다. 유사도는 전부 `packages/engine`·워커·ML 서비스가
벡터를 읽어 계산한다(§2.2). HNSW 인덱스 3개는 만들어져 있었지만 어떤 쿼리도 쓰지 않았다.

## 결과

- HNSW 인덱스를 삭제했다. 대규모 1:N 검색이 필요해지면 DB 검색이 아니라 복호화 후 앱 메모리 인덱스나
  별도의 보안 벡터 저장소를 검토한다.
- 차원 검사를 앱이 한다. 원래 `vector(512)`·`vector(256)` 컬럼 타입이 하던 일이다(`vector.ts`).
- 이행은 `pnpm db:deploy`(`packages/db/prisma/deploy.ts`)가 한다 — 암호문 채움과 행별 복호화 검증 →
  마이그레이션(평문이 남은 행이 있으면 삭제 전에 중단) → `VACUUM FULL`로 삭제된 평문을 데이터 파일에서 제거.
- 키를 잃으면 임베딩을 읽을 수 없다. 원본 사진이 있으면 사진 재검사와 프로파일 재빌드로 다시 만들 수 있지만,
  프로젝트가 고정한 과거 프로파일 버전의 centroid를 같은 값으로 되살리지는 못한다. 키는 비밀 저장소에 백업한다.
- 원본 사진은 저장 데이터 암호화라서, 버킷 권한을 가진 주체는 복호화된 사진을 받는다.
  접근 통제는 여전히 퍼블릭 차단과 15분 만료 presigned URL(§15)에 기댄다.

## 남는 평문 — 이 저장소 밖

- 이행 전에 떠 둔 DB 백업, WAL 아카이브, 복제본에는 평문 벡터가 남는다. 운영 절차로 폐기해야 한다.
- 스토리지 버저닝으로 남은 이전 버전은 재암호화할 수 없다. 현재 버전을 제자리 복사로 재암호화한 뒤
  이전 버전(noncurrent)을 지워야 디스크에서 평문이 사라진다.
